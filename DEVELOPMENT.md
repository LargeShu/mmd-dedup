## Пять правил проекта

### 1. Диски — только на чтение

Все скрипты открывают файлы строго на чтение (`'rb'`, `os.scandir`, `ffprobe`).
Ни удаления, ни перемещения, ни переименования. Всё, что создаётся, лежит
в `data/` и `reports/`.

Проверяется автоматически: гейт снимает контрольные суммы всего дерева до
и после полного прогона и требует совпадения.

### 2. Никаких путей в коде

Пути живут только в `config.json`, который не попадает в репозиторий.
Инструмент рассчитан на то, что его возьмут с другой раскладкой каталогов.

Загрузка — `L.load_config()`, объединение с флагами — `L.merge_roots()`.
Целевой диск (`target`) тоже оттуда: `TARGET_DRIVE` в `03_report.py`
инициализируется в `main()`, а не константой.

### 3. Пакеты — только в venv проекта

`scripts/.venv`. Системный Python не трогаем: ни `pip3 install`, ни `sudo pip`,
ни `--break-system-packages`.

`imagehash` подтягивает `numpy`, `scipy`, `PyWavelets` — порядка 150 МБ.

Без библиотек работают этап 1, `--stage exact` и этап 3; `exif` и `phash`
аккуратно пропускаются с подсказкой.

### 4. После правки — `./check.sh`

Полный набор: компиляция, ruff с security-набором, юнит-тесты, регрессионные
тесты, сквозной прогон, доказательство read-only. Около минуты.

Гейт **останавливается с диагнозом**, если venv недоступен или в нём нет
пакетов, — не переходит на системный Python. Ложный зелёный хуже красного.

### 5. Документация обновляется вместе с кодом

Меняется поведение — в том же заходе правится описание. Расхождение считается
дефектом наравне с ошибкой в коде: по этому описанию будут принимать решения
об удалении файлов.

Что синхронизируется: флаги, порядок признаков выбора «кого оставить», состав
отчётов, условия запуска дорогих проходов.

## Версия

`L.VERSION` в `mmdlib.py` — одна на весь проект. Отдельных версий у скриптов
нет намеренно: они передают работу друг другу через одну базу, и сочетание
«02 старой версии + 03 новой» незачем разрешать.

Версия видна в трёх местах: `--version` у любого скрипта, подвал
`decision.html`, ключ `app_version` в таблице `meta`. Последнее важнее, чем
кажется: обход длится часами, скрипты за это время правятся, и без штампа
причину странных данных в базе восстановить нечем.

`SCHEMA_VERSION` — про другое: совместимость файла базы. Растёт реже, только
когда меняется структура таблиц.

Поднимать `VERSION` вручную при изменении поведения, видимого пользователю.

## Диски: подключены ли они на самом деле

`L.проверить_диски()` и `L.сообщить_о_дисках()` — общие для всех этапов.

`os.path.isdir` недостаточно. Когда сетевая шара не примонтирована, macOS
оставляет на её месте **пустой локальный каталог** с тем же именем. Проверка
проходит, и начинается тихая беда: этап 1 находит ноль файлов и при `--prune`
вычищает инвентарь; этап 4 «переносит» дубли на системный диск вместо
хранилища. Оба случая выглядят как успех — ровно тот класс дефекта, из-за
которого в этом проекте всё сообщается вслух.

Различаются два уровня:

| признак | уровень |
|---|---|
| каталога нет, не каталог, не читается | стоп всегда |
| путь ведёт в `/Volumes`, `/mnt`, `/media`, но том системный | стоп всегда |
| каталог пуст | предупреждение; стоп при `строго=True` |

Пустой диск бывает законно, поэтому он останавливает работу только там,
где цена ошибки высока: `01_inventory --prune` и `04_apply --move`. Отказ
на ровном месте вреден не меньше молчания: от него отучаются флагом,
и проверка перестаёт защищать вообще. Снять её осознанно — `--skip-mount-check`.

`точка_монтирования()` поднимается вверх до смены `st_dev`, а не полагается
на `os.path.ismount`: корень диска в `config.json` может лежать **внутри**
тома — `/Volumes/video/300 Photos` это папка на томе `/Volumes/video`.

Перед работой каждый этап печатает диски с точкой монтирования и свободным
местом — так видно, с чем именно он собрался работать.

## Логика скриптов

### `mmdlib.py` — общее

Место, где живут решения, обязанные совпадать во всех скриптах.

| что | зачем |
|---|---|
| `load_config()`, `merge_roots()` | пути и целевой диск; единственный источник |
| `classify()` | расширения → `image`/`raw`/`video`/`audio`/`archive`/`sidecar`/`junk`/`other` |
| `is_junk_dir()` | служебные каталоги Synology и macOS |
| `init_db()` | схема SQLite и миграции |
| `originality_key()` | **единый порядок «кто ближе к оригиналу»** |
| `csv_safe()` | защита от formula injection в Excel |
| `md_text()` | экранирование имён файлов в markdown |
| `venv_notice()`, `human()`, `dur()`, `plural()` | вспомогательное |

`originality_key()` вынесена сюда после конкретного дефекта: поиск и отчёт
судили об оригинальности по разным правилам.

`archive` выделен отдельным классом не для дедупликации, а чтобы такие файлы
было видно: внутри может лежать фотоальбом, который скрипты не разберут.

### `mmdlib.merge_roots` — диски из конфига ИЛИ из флагов

Флаги `--root ИМЯ=ПУТЬ` раньше *дополняли* `config.json`. Это оказалось
ловушкой: запуск на паре тестовых каталогов молча тащил за собой настоящие
диски пользователя — они попадали в проверки, в план, в выбор оригинала.
Человек, набравший `--root`, имеет в виду «работай вот с этим». Теперь
правило простое: есть хоть один `--root` — работаем ровно по ним.

### `01_inventory.py` — карта

Обход в ширину, только `scandir`/`lstat`. Пакетная вставка каждые 2000 записей
вместе с отметкой «каталог обойдён», в одной транзакции.

**Инкрементальность по умолчанию.** Каталог перечитывается, только если
изменился его собственный `mtime`. Он меняется при добавлении, удалении
и переименовании файлов внутри — новые фото в старой папке не теряются.
Не ловится правка файла на месте; для этого `--restat`.

| флаг | что делает |
|---|---|
| без флагов | инкрементально |
| `--restat` | перечитать всё, сохранив базу |
| `--rescan` | стереть данные по дискам и начать с нуля |
| `-L 1..20` | ограничить глубину (пробный прогон) |
| `--prune` | убрать из базы записи о пропавших файлах |
| `--drive ИМЯ` | только один диск |

**Запись через `ON CONFLICT DO UPDATE`, а не `INSERT OR REPLACE`.** `REPLACE`
удаляет строку и вставляет новую с новым `id`, из-за чего таблица `sigs` —
часы хеширования — теряла привязку к файлам.

**Полнота обхода.** Недоступные каталоги, сбойные файлы, пропущенные симлинки,
обрезанные `-L` ветви пишутся в `scan_errors` и выводятся блоком «инвентарь
неполный». `scan_errors` чистится при каждом запуске, включая инкрементальный:
обход заново проходит по всем каталогам, поэтому всё переобнаруживается.

**Достоверность дат.** Считается доля файлов в папках, где у всех одинаковый
`mtime` — след массового копирования. Больше 10% — предупреждение.

Итоги считаются по базе, а не по счётчикам сессии.

### `02_signatures.py` — отпечатки

Стадии `exact`, `exif`, `phash`, `video`, `thumb`. Каждая берёт из базы только
необработанные строки, поэтому прерывание безопасно. Чтение в несколько потоков
(`--threads`, по умолчанию 8): узкое место — задержка сети, не процессор.

Стадию можно писать и короче: `--exact` вместо `--stage exact`.

**Версионирование рецептов.** `SIG_RECIPE` хранит версию алгоритма каждой
стадии в `meta`. Стадии не пересчитывают заполненные строки — на этом держится
возобновляемость. Но при смене алгоритма в базе оказались бы сигнатуры двух
поколений, и группировка молча смешала бы их. Поэтому версия сверяется при
запуске, и при расхождении стадия отказывается работать до `--recompute`.

**Меняете логику стадии — поднимите версию.**

**Прогресс по байтам для `exact` и `thumb`.** Стоимость единицы работы там
различается стократно, счётчик файлов о прогрессе не говорит ничего.
Скорость — по скользящему окну в 60 секунд: среднее с начала инертно
и маскирует переход к крупным файлам.

**Стадия `thumb`** делает превью **только для групп `exif` и `phash`** — там,
где файлы различаются. Точным копиям превью не нужны. Требует уже посчитанных
групп, поэтому запускается после первого прогона отчёта и не входит
в `--stage all`. Превью хранятся в базе, а не файлами: благодаря этому этап 3
не обращается к дискам.

**Журнал** `reports/signatures_log.csv` дописывается после каждой стадии,
включая прерванные.

**Два Ctrl+C.** Первый — аккуратная остановка с коммитом и записью журнала,
второй — немедленный выход. Второй нужен потому, что «аккуратно» иногда
означает «идёт запись», а пользователь не понимает, реагирует ли скрипт.

### `03_report.py` — группировка и отчёты

Работает только с базой, к дискам не обращается. Превью выгружаются из таблицы
`thumbs` в `reports/thumbs/`.

Единица решения — **один дубль**: конкретный файл-кандидат на удаление вместе
с оригиналом для сравнения. Раскладываются по папке, где лежит **дубль**,
а не оригинал: вопрос звучит как «что в этой папке лишнее». Одна группа
поэтому может попасть в несколько папок.

Пути в отчётах — **полные**, а не с логическим псевдонимом диска: их копируют
в Finder.

`decision.html` перезаписывается; markdown-чек-листы (`--md`) — никогда,
рядом появляются файлы с датой в имени.

**Три состояния решения** вместо двух: не разобрано, удалить дубль,
оставить обе, перевернуть пару. Хранятся числами 1/2/3 в `localStorage`
и переносятся в экспорт (`к_удалению` с флагом `переопределено`
и `оставлены_обе`), иначе после перегенерации отчёта разобранные пары
снова считались бы неразобранными.

**Ключ решения — `rid`, а не id файла.** Один файл попадает в несколько строк:
в группу `exact` и в группу `phash`, причём с разными оригиналами. Пока
состояние хранилось по id файла, отметка в одной строке молча ставилась
и в другой, а экспорт получался неоднозначным. `rid` собирается как
`метод:id_дубля:id_оригинала` — уникален для строки и стабилен между
перегенерациями.

**Строка обновляется на месте, список не перерисовывается.** Раньше любое
решение вызывало полную перерисовку, и строка мгновенно исчезала под фильтром
«только неразобранные» — убедиться, что получилось задуманное, было нельзя.
Обработчики висят на теле папки через делегирование, поэтому переживают
обновление содержимого строки. Явная уборка — кнопка «скрыть решённые».
**Массовые операции подчиняются тому же правилу.** Раньше «удалить всю папку»
перерисовывало папку целиком, и при включённом фильтре «только неразобранные»
тысяча строк исчезала разом — без объяснения и без возможности убедиться,
что нажато именно то, что задумано. Теперь строки обновляются на месте,
а в подвале появляется итог: сколько отмечено и как снять.

**Пустая папка обязана объяснить, почему она пустая.** Причин две, и они
разные: всё разобрано и скрыто фильтром — либо ничего не подошло под поиск.
В первом случае рядом кнопка «показать решённые».

Переворот меняет стороны местами по существу, а не только подписи: в экспорт
уходит `путь` = бывший оригинал, `оставить` = бывший дубль. Перед переворотом
считается, для скольких ещё строк этот файл служит оригиналом, и при
ненулевом счёте выводится предупреждение — `04_apply` такие строки отклонит.

**Сортировка папок — жадное правило, а не украшение.** Времени и внимания
у человека конечное количество, поэтому порядок папок решает, сколько удастся
освободить за вечер. Наибольший результат к любому моменту даёт сортировка
по отношению «выгода / стоимость» (правило Смита в теории расписаний), а не
по абсолютному размеру.

Стоимость решений здесь разная, и это меняет ответ. Папка точных копий
снимается **одним** нажатием «удалить всю папку» независимо от числа строк;
папку с похожими надо смотреть построчно. Поэтому:

```
стоимость = (есть ли неразобранные exact ? 1 : 0) + число прочих неразобранных
выгода    = неразобранные байты / стоимость
```

Числитель — **остаток**, а не исходный размер: статический ключ не знает,
что полпапки уже разобрано, и держал бы её наверху до конца.

**Порядок — снимок, а не живая величина.** Пересчёт после каждого решения
заставлял бы список плыть под руками: отметил строку — папки перескочили,
место потеряно. Порядок обновляется только по явному действию: смена
сортировки или направления, поиск, вкладка метода, кнопка «пересортировать».
Ничья разрешается путём, иначе равные папки скачут между перерисовками
без причины.

Выбор сортировки хранится в `localStorage` отдельным ключом `…:вид`.
Отдельно от решений намеренно: потеря порядка — неудобство, потеря
решений — потерянная работа.

**Фильтр по типу совпадения.** Отчёт открывается на `exact`: там основная
масса и механическая работа. Переключение не перезагружает данные — все строки
уже в памяти, меняется только выборка. Точные копии рендерятся в компактном
режиме без превью: файлы побайтово одинаковы, показывать две одинаковые
картинки незачем.

Цвета: `exact` зелёный, `exif` янтарный, `phash` фиолетовый. Красный
не используется сознательно — `phash` требует внимания, но ошибкой не является,
и светофорная метафора здесь ломается намеренно.

**Отчёт проверяет сам себя.** Перед сборкой `decision.html` считается
`selfcheck()`: уникальность `rid`, наличие оригинала у каждой строки,
несовпадение дубля с оригиналом, сходимость счётчиков папок и строк.
Юнит-тесты проверяют правила, которые уже известны, и на стендах в десяток
файлов; здесь проверка идёт на реальных ста тысячах. Нарушения печатаются
блоком «САМОПРОВЕРКА», предупреждения — отдельно (файл к удалению в одной
строке и оригинал в другой; нулевой размер).

### `04_apply.py` — исполнение решений

Единственный скрипт, который меняет файлы. По умолчанию — предпросмотр.

**Карантин на том же томе, что и файл.** `shutil.move` внутри одной файловой
системы — переименование: мгновенное, атомарное, без трафика. Между томами —
копирование целиком с последующим удалением. Пока карантин создавался
в каталоге проекта, у пользователя с архивом на NAS и проектом на Mac перенос
70 ГБ шёл по сети. Умолчание теперь `<корень диска>/_MMD_quarantine/<дата>`,
`--quarantine` оставлен для случая «унести карантин на другой носитель»
и сопровождается предупреждением в плане.

Следствие: журналов столько, сколько дисков, и каждый лежит рядом со своим
карантином. Карантин и запись о том, откуда что взято, должны переезжать
и удаляться вместе. `--undo` принимает папку и находит журналы сам —
иначе один из них однажды забудут.

**Вывод отвечает на три вопроса: когда начали, как идём, чем кончилось.**
В начале — версия и время запуска: прогон на сетевом диске длится часами,
и вернувшись к терминалу через полдня, надо понимать, сколько он уже работает.
В конце — блок «ИТОГ»: сколько перенесено, за какое время, с какой скоростью,
куда лёг карантин и был ли это перенос или копирование между томами.
Раньше вывод обрывался последней строкой прогресса, и итог приходилось
собирать глазами по всей простыне.

**Прогресс печатается по времени, а не по числу файлов.** Шаг «каждые 200»
ничего не знает о скорости: на быстром томе он заваливает экран, на сетевом
молчит минутами. Раз в три секунды с темпом в МБ/с и остатком — знает.

**Предпросмотр сообщает о ходе работы.** Проверка 2 700 решений по сети идёт
минутами, и раньше это выглядело как зависание. `realpath` кешируется
(один оригинал повторяется в десятках строк), `isfile` + `getsize` заменены
одной `stat`.

**Сообщение при Ctrl+C зависит от того, начался ли перенос.** Обработчик писал
«уже перенесённые файлы остались в карантине» даже в предпросмотре, где
не тронут ни один файл.

### `app_assets.py` — вёрстка отчёта

CSS и JS вынесены отдельным модулем: в f-строках Python фигурные скобки
пришлось бы удваивать. Данные подставляются одной заменой `__DATA__`.

**Подсказки называют файл, а не сторону.** Флажок и кнопка переворота
подписываются из состояния строки: после переворота флажок обещает удалить
именно левый файл и печатает его имя. Неизменная подпись «отметить дубль
к удалению» врала ровно в перевёрнутых парах.

**Блок `JS` — сырая строка Python (`r"""`).** Обратная косая в JS-коде иначе
исчезает при чтении файла Python, а не при выводе, и ошибка проявляется
только в браузере.

**JSON внутри `<script>` экранируется** (`</` → `<\/`): имя файла вида
`<script>alert(1)</script>.jpg` иначе закрывает тег раньше времени
и превращает данные в исполняемый код. `json.dumps` от этого не защищает.

Логика этого модуля проверяется `tests/test_app.js` — под node, с DOM-заглушкой,
на JS, вынутом из **готового** отчёта. Правило «нашли баг — сначала тест»
действует и здесь: коллизия ключей решений найдена именно так.

## База `data/inventory.db`

| таблица | что хранит | кто заполняет |
|---|---|---|
| `files` | метаданные ФС, класс, метка обхода | этап 1 |
| `scanned_dirs` | обойдённые каталоги и их `mtime` | этап 1 |
| `scan_errors` | что не удалось прочитать | этап 1 |
| `sigs` | SHA-256, EXIF, pHash, разрешение, длительность | этап 2 |
| `thumbs` | превью (BLOB) | этап 2, стадия `thumb` |
| `groups`, `group_members` | найденные группы | этап 3 |
| `meta` | корни дисков, времена, версии рецептов | все |

Связь `sigs.file_id → files.id` — самое хрупкое место: в ней часы работы
этапа 2. Любая правка `files` обязана сохранять `id`.

Схема версионируется (`meta.schema_version`, сейчас 7), старые базы мигрируются
при запуске без потери данных.

Повторный запуск не задваивает данные: `UNIQUE (drive, relpath)`.

## Публичное и локальное

Часть файлов не уходит на GitHub: правила git, инструкция по доступу, заметки
по конкретной установке, чужие материалы. Перечень — в `.gitignore`
с причиной у каждой строки.

Двух версий README нет намеренно. **Документация в репозитории описывает код,
локальный `LOCAL.md` — конкретную установку**, и пересечения между ними нет,
поэтому расходиться нечему. Две версии одного текста разошлись бы, а гейт
такого не ловит.

Что гейт ловит — шаг 11: ссылку из отслеживаемого файла на файл вне
репозитория. На GitHub такая ссылка битая, а у автора открывается.

## Известные компромиссы

Осознанные, зафиксированы намеренно.

**`load_files()` держит всю библиотеку в памяти.** Порядка 1 КБ на файл:
200 000 файлов — около 200 МБ. Для целевого объёма приемлемо.

**`os.scandir()` материализует каталог целиком.** Каталог с миллионом файлов
в одной папке даст всплеск памяти. На фотоархиве такого не бывает.

**`group_phash` внутри корзины сравнивает пары квадратично.** Ограничено
порогом в 400 элементов, худший случай — 80 000 сравнений на корзину.

**`--prune` не работает после неполного обхода**, даже если настаивать:
удалять записи о файлах, которые просто не просматривались, недопустимо.
