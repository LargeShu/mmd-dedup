# Инвентаризация фотоархива и поиск дубликатов

Инструмент для тех, у кого фотографии за много лет расползлись по нескольким
дискам, папкам и резервным копиям, и непонятно, что где лежит, сколько места
съедено копиями и что можно убрать без потерь.

Работает локально и ничего никуда не отправляет. Поиск и отчёты **не трогают
файлы вообще**; убрать отмеченное можно отдельным скриптом, и он не удаляет,
а переносит в карантин — с возможностью вернуть всё обратно.

## Что он делает

1. **Составляет карту** всех медиафайлов на указанных дисках: сколько, какого
   типа, какого объёма, по каким папкам и годам.
2. **Находит дубликаты** тремя независимыми способами — от абсолютно
   достоверного до вероятностного.
3. **Готовит отчёт** с превью, данными съёмки и галочками: вы просматриваете
   и отмечаете, что готовы удалить. Решения сохраняются.

Типичный результат на реальном архиве: 126 тысяч файлов, 520 ГБ, из них
21 тысяча групп точных копий и около 70 ГБ, которые можно освободить.

## Чего он не делает

- **Не удаляет файлы.** Даже скрипт исполнения решений только переносит их
  в карантин; удаление папки карантина остаётся за вами. Этапы 1–3 открывают
  файлы строго на чтение.
- Не заливает ничего в облако и не выходит в интернет.
- Не заглядывает внутрь архивов (`.zip`, `.rar`) — но показывает, что они есть.
- Не решает за вас, что дубль, а что нужная копия. Он показывает факты
  и рекомендацию; решение остаётся за человеком.

## Установка

Нужен Python 3.10 или новее. Проверить: `python3 --version`.

```bash
cd путь/к/проекту
./setup.sh
```

Скрипт проверит версию Python, создаст окружение, поставит зависимости,
заведёт каталоги `data/` и `reports/`, создаст `config.json` из образца
и покажет, доступны ли указанные в нём диски. Повторный запуск безопасен.

Вручную, если хочется контроля:

```bash
python3 -m venv scripts/.venv
scripts/.venv/bin/pip install -r requirements.txt
```

Библиотеки ставятся **только в это окружение**, системный Python не трогается.
Удалить бесследно: `rm -rf scripts/.venv`.

Полезно, но необязательно: `ffmpeg` — нужен для кадров из видео
(`brew install ffmpeg` на macOS).

**Всё работает и без библиотек**, просто в урезанном виде: карта архива и поиск
точных копий доступны на голом Python. Отпадают только разбор EXIF и поиск
похожих кадров.

## Настройка: `config.json`

Единственное место, где живут пути к вашим дискам. В коде их нет.

```bash
cp config.example.json config.json
```

Впишите свои:

```json
{
  "drives": {
    "photo": "/Volumes/photo",
    "archive": "/Volumes/backup/Фото 2015"
  },
  "target": "photo"
}
```

| поле | смысл |
|---|---|
| `drives` | короткие имена дисков и пути к ним. Имена произвольные, они попадают в базу и отчёты |
| `target` | куда всё сводим: при выборе «какой файл оставить» файл на этом диске получает преимущество |

Дисков может быть сколько угодно, не обязательно два. Пути могут быть любыми —
сетевая шара, внешний диск, папка в домашнем каталоге.

Можно обойтись и без файла, задав диски флагами:

```bash
scripts/.venv/bin/python scripts/01_inventory.py \
    --root "фото=/Volumes/photo" --root "бэкап=/mnt/old"
```

`config.json` не попадает в репозиторий — у каждого он свой.

## Быстрый старт

Четыре команды. Все запускаются из корня проекта.

```bash
# 1. Карта архива: что где лежит. Только метаданные, содержимое не читается
scripts/.venv/bin/python scripts/01_inventory.py

# 2. Сколько времени займёт следующий шаг — узнать заранее, ничего не читая
scripts/.venv/bin/python scripts/02_signatures.py --plan

# 3. Снятие «отпечатков»: хеши, даты съёмки, перцептивные хеши
scripts/.venv/bin/python scripts/02_signatures.py --stage all

# 4. Отчёт
scripts/.venv/bin/python scripts/03_report.py
```

Откройте `reports/decision.html`.

Хотите превью в отчёте — добавьте два шага после первого запуска отчёта:

```bash
scripts/.venv/bin/python scripts/02_signatures.py --stage thumb
scripts/.venv/bin/python scripts/03_report.py
```

**Любой этап можно прервать Ctrl+C** и запустить снова — работа продолжится
с места остановки, ничего не потеряется и не пересчитается заново.

## Как это работает: четыре этапа

Разделение не формальное: каждый следующий этап дороже предыдущего, и работает
он только там, где предыдущий нашёл смысл искать.

```
 config.json
      │
      ▼
 ① inventory ──► карта: путь, размер, дата.   Файлы НЕ открываются
      │            data/inventory.db
      ▼
 ② signatures ─► отпечатки: SHA-256, EXIF, pHash.   Файлы читаются
      │            стадии exact / exif / phash / thumb
      ▼
 ③ report ─────► группы дублей + отчёты.   Диски НЕ читаются
      │            reports/decision.html
      ▼
   человек ────► галочки: что удалить
```

### ① Инвентаризация

Обходит каталоги и записывает только то, что отдаёт файловая система: имя,
размер, дата изменения. Ни один файл не открывается, поэтому этап быстрый даже
на сетевом диске.

```bash
scripts/.venv/bin/python scripts/01_inventory.py
scripts/.venv/bin/python scripts/01_inventory.py -L 2   # пробный, 2 уровня вглубь
```

Повторный запуск **не начинает заново**: каталог перечитывается, только если
изменилась его дата — то есть если внутри что-то добавили, удалили или
переименовали. Новые фото в старой папке не потеряются.

Если что-то не удалось прочитать — недоступные папки, битые ссылки, обрезанные
флагом `-L` ветви, — это попадает в отчёт отдельным блоком «инвентарь
неполный». Молчаливой потери данных быть не должно.

### ② Отпечатки

Здесь файлы читаются, поэтому этап делится на стадии, и каждая запускается
отдельно.

```bash
scripts/.venv/bin/python scripts/02_signatures.py --plan    # оценка, ничего не читает
scripts/.venv/bin/python scripts/02_signatures.py --exact   # точные копии
scripts/.venv/bin/python scripts/02_signatures.py --exif    # даты съёмки
scripts/.venv/bin/python scripts/02_signatures.py --phash   # похожие кадры
scripts/.venv/bin/python scripts/02_signatures.py --thumb   # превью для отчёта
```

| стадия | что делает | по каким файлам |
|---|---|---|
| `exact` | SHA-256 содержимого | только те, чей размер совпал с другим файлом — у остальных копий быть не может |
| `exif` | дата съёмки, камера, разрешение | все изображения; читается только заголовок |
| `phash` | перцептивный хеш | все изображения; полное декодирование |
| `thumb` | превью для отчёта | только файлы из групп, где кадры **различаются** |

Отбор кандидатов для `exact` — главная экономия: файл с уникальным размером
не может иметь побайтовой копии, читать его бессмысленно.

Каждый прогон пишет строку в `reports/signatures_log.csv`: когда начали,
сколько заняло, сколько прочитано, с какой скоростью. Прерванные прогоны тоже
записываются — они и интересны при разборе.

### ③ Отчёт

```bash
scripts/.venv/bin/python scripts/03_report.py
scripts/.venv/bin/python scripts/03_report.py --md   # плюс чек-листы для Obsidian
```

Работает только с базой, **к дискам не обращается вовсе** — даже превью берутся
из базы, а не с диска.

## Три способа найти дубликат

Они разные по надёжности, и путать их не стоит.

### Точные копии (`exact`)

Совпадает SHA-256 — файлы побайтово одинаковы. Достоверность абсолютная,
смотреть глазами не нужно, решение механическое.

### Один кадр в разных версиях (`exif`)

Совпадает дата съёмки + модель камеры + серийный номер. Так находятся пары
RAW+JPEG, экспорт в другом качестве, копия после редактора.

Проверять выборочно: RAW и JPEG одного кадра иногда хранят намеренно.

### Визуально похожие (`phash`)

Единственный **вероятностный** метод. Изображение сжимается до грубой
64-битной «подписи», устойчивой к изменению размера и качества. Похожие
подписи — вероятно, один и тот же кадр.

Ловит: ресайзы, пересохранения, смену формата, слабый кроп, водяные знаки.

**Обязательно смотреть глазами.** Сюда закономерно попадают серии кадров
подряд и разные снимки одной сцены — это не дубликаты.

Строгость задаётся флагом:

```bash
scripts/.venv/bin/python scripts/03_report.py --phash-distance 3   # строже
scripts/.venv/bin/python scripts/03_report.py --phash-distance 6   # свободнее
```

Менять порог можно сколько угодно — **пересчитывать отпечатки не нужно**,
это параметр группировки, а не хеширования.

Технические подробности метода — в [ALGORITHM.md](ALGORITHM.md).

## Как выбирается, какой файл оставить

В каждой группе один файл помечается «ОСТАВИТЬ». Порядок признаков:

1. дата съёмки совпадает с искомой (только в режиме точечного поиска)
2. файл на **целевом** диске из `config.json`
3. путь без признаков производной (`WhatsApp`, `Screenshots`, `копия`, `export`)
4. имя без суффиксов `_2`, `(1)`, `copy`, `small`
5. **EXIF-дата съёмки сохранена**
6. больше пикселей
7. больше байт
8. более ранняя дата
9. короче путь

Пункт 5 стоит выше разрешения намеренно. Оригинал от камеры хранит EXIF,
а пересохранение мессенджером или редактором обычно его стирает — поэтому
апскейл без метаданных не должен обходить настоящий оригинал.

Это **рекомендация**, а не действие.

## Работа с отчётом

Откройте `reports/decision.html` в браузере.

Дубликаты сгруппированы **по папке, где они лежат**, а не по папке оригинала.
Раздел `/Volumes/photo/iPhone Lev/2014` отвечает на вопрос «что в этой папке
лишнее» — и папку можно разобрать целиком.

Каждая строка — одно решение: слева файл-кандидат на удаление, справа
оригинал, который остаётся. У обоих превью, полный путь и данные съёмки.

### Разделение по типу совпадения

Точных копий обычно на порядок больше, чем всего остального, и работа с ними
принципиально другая: механическая, без разглядывания. Поэтому отчёт открывается
на вкладке **точные копии**, а переключатель вверху отделяет их от того, что
требует внимания.

| вкладка | цвет | что это значит |
|---|---|---|
| точные копии | зелёный | побайтово одинаковы, решение механическое |
| один кадр | янтарный | RAW+JPEG, экспорт — проверьте выборочно |
| похожие | фиолетовый | обязательно смотреть глазами |

Фиолетовый вместо красного выбран намеренно: `phash` не опаснее остальных,
он требует другого рода внимания. Красный означал бы ошибку, а её здесь нет.

**У точных копий превью не показываются.** Файлы побайтово одинаковы —
две идентичные картинки рядом были бы визуальным шумом. Строки выводятся
компактно, чтобы за экран помещалось больше.

### Три решения по каждой паре, а не два

Автоматика судит по формальным признакам — размеру, дате, разрешению —
и **не знает контекста**. Снимок в папке «Надежда Барабанова» осмысленнее
того же файла в общей куче, хотя по метаданным они неразличимы. Альбом
и папка проекта могут содержать один файл совершенно осознанно.

Поэтому у каждой строки три действия:

| кнопка | что означает |
|---|---|
| ☐ галочка | удалить дубль, оставить предложенный оригинал |
| `обе` | **оставить обе копии** — файлы связаны осознанно, трогать не надо |
| `⇄` | **поменять местами** — оставить левый, удалить правый |

Это важнее, чем кажется. Раньше «не отмечено» значило одновременно
«ещё не смотрел» и «посмотрел, решил оставить обе» — из-за чего фильтр
«только неразобранные» никогда не опустошался и дойти до конца было
невозможно.

Повторное нажатие снимает решение: передумать можно всегда.

**Решённая строка остаётся на месте**, а не исчезает под фильтром. Это
особенно важно для переворота: надо своими глазами убедиться, что стороны
поменялись правильно. Когда закончите с участком, нажмите **«скрыть
решённые»** в шапке — список перестроится.

На уровне папки работают обе массовые операции: `удалить всю папку`
и `оставить обе` — второе как раз для случая «альбом против проекта».

**Осторожно с переворотом.** Один оригинал часто служит эталоном для
нескольких дублей. Если перевернуть такую пару, файл окажется
одновременно удаляемым и оригиналом — отчёт предупредит об этом, а
`04_apply` такие строки отклонит, ничего не тронув.

| возможность | где |
|---|---|
| три решения по строке | ☐ / `обе` / `⇄` |
| «удалить всю папку» и «оставить обе» | в заголовке папки |
| «копировать путь» | у каждого файла и у каждой папки |
| фильтр «только неразобранные» | в шапке |
| сортировка папок | список «сначала:» в шапке |
| поиск по пути и имени | в шапке |
| счётчик освобождаемого места | в шапке, обновляется на лету |
| «Скачать решения (JSON)» | в шапке |

### С чего начинать: сортировка папок

Список «сначала:» в шапке задаёт порядок папок.

| пункт | когда полезен |
|---|---|
| **выгода за решение** (по умолчанию) | больше всего места за меньшее число действий |
| неразобранный объём | сколько ещё можно освободить именно здесь |
| общий объём | размер папки целиком, независимо от разобранного |
| неразобранных строк / всего дублей | когда важно число, а не байты |
| путь | привычный алфавитный порядок |

«Выгода за решение» учитывает, что **папка точных копий снимается одним
нажатием** «удалить всю папку», сколько бы строк в ней ни было, а похожие
смотрят построчно. Тысяча точных копий на 9 ГБ стоит одного решения, пять
похожих на 200 МБ — пяти. По абсолютному размеру они встали бы в правильном
порядке случайно.

Считается **остаток**: разобранная наполовину папка опускается вниз сама.

Порядок при этом — снимок, а не живая величина: он **не меняется от ваших
решений**, иначе список плыл бы под руками и место в работе терялось.
Пересчитать явно — кнопка «пересортировать». Стрелка рядом переключает
направление. Выбор запоминается вместе с остальными настройками отчёта.

### Про сохранение решений — важное

Галочки сохраняются в хранилище браузера. Оно привязано к конкретному браузеру
и профилю, чистится вместе с кэшем и не попадает в резервные копии.

**Поэтому кнопка «Скачать решения» — не украшение, а основной способ сохранить
работу.** Файл `decisions_*.json` положите рядом с проектом: он переживёт что
угодно, его можно передать коллеге и загрузить обратно кнопкой «Загрузить».

Отчёт `decision.html` **перезаписывается** при каждой генерации. Если вы уже
проставили галочки — сначала выгрузите решения в файл.

### Если ссылка на файл не открывается

Браузеры по-разному относятся к переходу на локальный файл: Safari обычно
пускает, Chrome и Firefox часто блокируют молча. Это не ошибка отчёта.

Надёжный путь — кнопка **«копировать путь»**, она работает везде. Дальше
в macOS: `Cmd+Shift+G` в Finder и вставить. В терминале: `open <путь>`
или `open -R <путь>`, чтобы показать файл в папке.

### Другие файлы отчёта

| файл | что внутри |
|---|---|
| `decision.html` | основной интерактивный отчёт |
| `00_summary.md` | объёмы, форматы, распределение по годам |
| `folder_map.csv` | карта всех папок |
| `overlap_folders.csv` | папки-тёзки на разных дисках — кандидаты на слияние |
| `dup_exact.csv`, `dup_exif.csv`, `dup_similar.csv` | полные списки групп |
| `signatures_log.csv` | журнал прогонов |
| `decision*.md` | чек-листы для Obsidian, по флагу `--md` |

CSV открываются двойным щелчком в Excel и Numbers: разделитель `;`,
кодировка UTF-8 с BOM.

## Точечный поиск конкретного файла

Отдельная задача: найти оригинал одной фотографии, не запуская весь конвейер.

```bash
# по имени
scripts/.venv/bin/python scripts/00_find_original.py IMG_1238.JPG

# если известна дата съёмки — самый надёжный признак
scripts/.venv/bin/python scripts/00_find_original.py 1238 \
    --date "24.12.2008 13:24" --tolerance 300

# если есть копия файла на руках — ответ будет однозначным
scripts/.venv/bin/python scripts/00_find_original.py 1238 --ref ~/Downloads/1238.JPG
```

Ищет в два прохода: сначала дешёвый по именам и датам файлов (находки
печатаются сразу), затем — при необходимости — дорогой по EXIF всех
изображений. Второй проход включается, только если первый не дал ни одного
кандидата, подтверждённого датой.

**Совпадение имени ничего не доказывает.** Файл `IMG_1238_2.JPG` с датой
съёмки 2018 года при поиске снимка 2008 года — другой кадр, у которого просто
совпал кусок имени. Такой кандидат уходит вниз списка с пометкой
`✗ ДАТА НЕ ТА`, а не возглавляет его.

Результат сохраняется в `reports/find_*.csv`.

## Сколько это займёт времени

Всё упирается в скорость диска, не в процессор. Ориентиры с реального архива
на 126 тысяч файлов и 520 ГБ по сети:

| этап | время |
|---|---|
| инвентаризация | 15–20 минут |
| `exact` (133 ГБ к чтению) | 30–60 минут |
| `exif` (114 тыс. изображений) | ~30 минут |
| `phash` (114 тыс. изображений) | ~1 час |
| `thumb` (только различающиеся) | зависит от числа групп |
| отчёт | секунды |

Точную оценку по вашим данным даст `--plan` — он ничего не читает,
а считает по уже собранной карте.

Все этапы прерываемы и продолжаются с места остановки, так что запускать
можно частями.

## Частые вопросы

**Он точно ничего не удалит?**
Этапы 1–3 — точно: они открывают файлы только на чтение, и это проверяется
автоматически контрольной суммой всего дерева до и после прогона.
Этап 4 меняет файлы, но только по вашему явному решению, только с флагом
`--move`, и не удаляет их, а переносит в карантин. Возврат — одной командой.

**Можно прервать на середине?**
Да, Ctrl+C на любом этапе. Посчитанное сохранено, повторный запуск продолжит.

**Нужно ли удалять базу перед повторным запуском?**
Нет. Повторный запуск обновляет данные на месте и не задваивает их.
Удалять стоит, только если `sqlite3 data/inventory.db "PRAGMA integrity_check"`
отвечает не `ok`.

**Я поменял порог похожести — надо пересчитывать?**
Нет. Порог применяется при группировке, отпечатки от него не зависят.

**Файлов стало больше/меньше, что делать?**
Просто запустить инвентаризацию снова. Изменившиеся папки перечитаются, новые
файлы добавятся. Для удалённых: `01_inventory.py --prune` уберёт их записи
из базы (сами файлы не трогаются).

**Работает на Windows 11?**
Скрипты — да. Оговорки в разделе [Windows](#windows) ниже.

**Можно передать отчёт коллеге?**
`decision.html` самодостаточен, но превью лежат отдельной папкой `thumbs/` —
передавайте вместе с ней. Решения в JSON переносятся между машинами.

## Что делать с отмеченным

Отдельный скрипт исполняет решения из выгруженного JSON.

```bash
# 1. Посмотреть план. Ничего не делает
scripts/.venv/bin/python scripts/04_apply.py --decisions reports/decisions_*.json

# 2. Выполнить
scripts/.venv/bin/python scripts/04_apply.py --decisions reports/decisions_*.json --move

# 3. Если что-то не так — вернуть всё обратно
scripts/.venv/bin/python scripts/04_apply.py --undo "/Volumes/photo/_MMD_quarantine/2026-08-10_18-30"
```

**Файлы не удаляются, а переносятся в карантин** с сохранением структуры
каталогов. Удаление необратимо, перенос — нет. Когда убедитесь, что ничего
нужного не пропало, удалите папку карантина обычным способом.

**Карантин создаётся на том же диске, где лежит файл:**
`<корень диска>/_MMD_quarantine/<дата-время>`. Это не про удобство. Перенос
внутри одной файловой системы — переименование: мгновенное и атомарное, файл
в каждый момент существует либо там, либо там. Перенос между дисками —
копирование с последующим удалением, и для сетевого хранилища это часы
трафика вместо секунд, а обрыв связи посреди копирования оставляет файл
в неопределённом состоянии.

План показывает для каждого диска, куда пойдёт карантин и один ли это том.
`--quarantine ПАПКА` собирает всё в один каталог — осмысленно, когда карантин
намеренно уносят на другой носитель; тогда план предупредит о копировании.

Журналов столько, сколько задействовано дисков, и каждый лежит рядом со своим
карантином. `--undo` принимает и отдельный журнал, и папку карантина целиком.

Перед каждым файлом выполняются проверки, и при любой неудаче файл
пропускается:

| проверка | зачем |
|---|---|
| файл существует, размер совпадает с решением | база могла устареть |
| **оригинал существует и читается** | иначе удалили бы единственную копию |
| **оригинал сам не отмечен к удалению** | иначе исчезли бы все копии кадра |
| файл внутри настроенных дисков | защита от опечатки в пути |
| `--verify-hash` | побитовая сверка дубля с оригиналом |

Отклонённые показываются с причиной. Случаи «потеряли бы единственную копию»
выделяются отдельно — их стоит разобрать руками.

Журнал в карантине фиксирует каждый перенос: откуда, куда, размер, хеш.
По нему работает возврат.

## Windows

Скрипты конвейера работают: всё на стандартном Python, пути через `os.path`,
ссылки в отчёте формируются корректно (`file:///C:/...`), вывод в консоль
переключается на UTF-8 — иначе символы вроде `✓` роняли бы процесс в `cp866`.

Что отличается:

| | macOS / Linux | Windows |
|---|---|---|
| установка | `./setup.sh` | вручную, см. ниже |
| проверки качества | `./check.sh` | нужен WSL или Git Bash |
| открыть файл из отчёта | `open <путь>` | вставить путь в проводник |
| показать файл в папке | `open -R <путь>` | `explorer /select,<путь>` |

Установка на Windows:

```powershell
python -m venv scripts\.venv
scripts\.venv\Scripts\pip install -r requirements.txt
mkdir data, reports
copy config.example.json config.json
```

Дальше вместо `scripts/.venv/bin/python` пишите
`scripts\.venv\Scripts\python`.

Пути в `config.json` — с прямыми слэшами или удвоенными обратными:
`"C:/Users/ivan/Photos"` либо `"C:\\Users\\ivan\\Photos"`.

**Одна оговорка про NTFS.** Файловая система не различает регистр, а база —
различает. Если в архиве есть `IMG.JPG` и `img.jpg`, на Windows это один файл,
а инструмент сочтёт их разными записями. На практике встречается редко.

`ffmpeg` для превью из видео ставится отдельно и должен быть в `PATH`.

## Ограничения, о которых стоит знать

- **Похожесть транзитивна.** Если A похож на B, а B на C, все трое попадут
  в одну группу, даже когда A и C не похожи. На сериях кадров это даёт длинные
  цепочки — ещё одна причина смотреть глазами.
- **Полнота поиска похожих ограничена порогом.** Все пары в пределах порога
  будут найдены, но пары чуть за ним — нет.
- **Крупные однородные корзины отбрасываются.** Однотонные кадры, сканы,
  пустые превью слиплись бы в одну группу на тысячи файлов. Сколько отброшено —
  печатается.
- **Даты файлов часто врут.** После массового копирования `mtime` — это дата
  копирования. Инструмент считает долю таких файлов и предупреждает; опирайтесь
  на EXIF.
- **Стёртый EXIF.** У файлов после мессенджеров и редакторов даты съёмки нет,
  в `exif`-группы они не попадут. Их ловит `phash`.
- **RAW+JPEG пары** намеренно попадают в `exif`-группы. Если вы храните их
  парами сознательно, эти группы надо пропускать.
- **Внутрь архивов** конвейер не заглядывает.
